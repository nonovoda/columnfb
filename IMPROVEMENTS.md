# Улучшения для `clmnPresetsManager.js`

## Что делает текущий скрипт

Скрипт уже умеет:
- выгружать пресет колонок + размеры колонок в JSON;
- импортировать пресет в несколько ad account;
- переносить кастомные метрики (derived metrics) между аккаунтами;
- показывать простую UI-форму поверх Ads Manager.

## Ключевые проблемы текущей реализации

1. **Монолит в одном файле**
   - API-клиент, бизнес-логика, UI и упаковка bookmarklet смешаны в одном файле.
   - Это усложняет тестирование и развитие.

2. **Риски безопасности токена**
   - Используется глобальный `__accessToken` и bookmarklet с `eval(...)`.
   - Для внутреннего инструмента это рабоче, но с точки зрения безопасности/поддержки — хрупко.

3. **Слабая валидация импортируемого JSON**
   - Проверяется только наличие `preset`, но нет строгой схемы.
   - Ошибки структуры могут проявиться только во время API-запросов.

4. **Неполная обработка ошибок Graph API**
   - Ответы API почти не нормализуются.
   - Нет стандартизированного ретрая, бэк-оффа, понятной классификации ошибок.

5. **Рейт-лимит и производительность**
   - Импорт по аккаунтам строго последовательно с фиксированной паузой 1 секунда.
   - Нет адаптивного параллелизма и нет уважения к headers/кодам лимитов.

6. **Хрупкий UI/UX**
   - Инлайн-стили, hardcoded желтый дизайн, `alert/confirm`.
   - Нет прогресс-бара по аккаунтам, нет повторной попытки для failed аккаунтов.

7. **Версионирование формата пресета не формализовано**
   - Файл экспорта не содержит явный `schemaVersion` + миграции.
   - При изменении структуры возможны несовместимости.

8. **Невозможность dry-run**
   - Перед применением нет режима «показать, что будет изменено».

9. **Неполная идемпотентность по custom metrics**
   - Метрики создаются заново, нет стратегии сопоставления по fingerprint (имя+формула+тип).
   - Возможны дубликаты.

10. **Сложность поддержки bookmarklet-сборки**
    - Ручная сериализация функций через `.toString()` хрупкая при рефакторинге.

## Как улучшить (практический roadmap)

### Этап 1 — быстрая стабилизация (1–2 дня)

- Добавить строгую валидацию импорта через JSON Schema (например Ajv).
- Ввести единый `ApiError` с разбором ошибок Graph API.
- Добавить `schemaVersion` в экспортируемый JSON.
- Добавить «dry-run»: список аккаунтов, создаваемых метрик, итоговых действий.
- Улучшить лог: сводка по каждому аккаунту + экспорт отчета о выполнении.

### Этап 2 — надёжность и масштаб (2–4 дня)

- Ввести адаптивный retry (exponential backoff + jitter) для 429/5xx.
- Сделать ограниченный параллелизм (например 2–4 аккаунта одновременно).
- Реализовать идемпотентность метрик:
  - сначала загружать существующие метрики аккаунта;
  - матчить по `name + formula + format_type`;
  - создавать только отсутствующие.
- Добавить режим «повторить только failed аккаунты».

### Этап 3 — архитектура и DX (4–7 дней)

- Разделить код на модули:
  - `api/graphClient.js`
  - `domain/presets.js`
  - `domain/customMetrics.js`
  - `ui/modal.js`
  - `bookmarklet/build.js`
- Перевести на TypeScript для типобезопасности DTO и ответов API.
- Добавить unit-тесты доменной логики (валидация, mapping id, миграции схемы).
- Добавить e2e smoke-test (моки API).

## Что можно переделать радикально

1. **Из bookmarklet в расширение браузера (Chrome Extension MV3)**
   - Плюсы: лучше UX, управляемые permissions, хранение настроек, стабильные обновления.
   - Минусы: требуется упаковка/дистрибуция.

2. **Из клиентского скрипта в маленький internal web app**
   - Backend хранит шаблоны и историю применений.
   - Можно дать audit trail: кто/когда/куда применил preset.

3. **Гибрид**
   - Лёгкое расширение/скрипт как UI, а тяжелая логика импорта — через backend API.
   - Это лучше для командной эксплуатации.

## Минимальный новый формат JSON (пример)

```json
{
  "schemaVersion": "2.0.0",
  "exportedAt": "2026-05-13T00:00:00Z",
  "source": {
    "accountId": "1234567890",
    "apiVersion": "v23.0",
    "toolVersion": "2025.12.12"
  },
  "preset": { "...": "..." },
  "sizes": [],
  "customMetrics": []
}
```

## Приоритетные изменения прямо сейчас (если делать только 5)

1. JSON Schema + проверка до старта импорта.
2. Retry/backoff для API.
3. Dry-run + предпросмотр diff.
4. Идемпотентная синхронизация custom metrics.
5. Модульная декомпозиция (минимум API/Domain/UI).

## Итог

Скрипт функционально полезный уже сейчас, но для долгосрочного использования его лучше перевести из «одноразового bookmarklet-утилита» в структурированный инструмент с:
- формализованным форматом данных,
- предсказуемой обработкой ошибок,
- масштабируемым импортом,
- и более безопасным способом доставки.
